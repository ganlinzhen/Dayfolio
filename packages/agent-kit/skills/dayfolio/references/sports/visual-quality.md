# 赛事页面的视觉生成与验收

用于新建页面、重做视觉以及验证本技能的生成效果。数据更新仍遵守原页面身份与偏好保护，不顺手重做 UI。

## 复用设计能力，区分宿主与作品

- 环境中有 `impeccable` 时，读取其入口与适用的工具界面参考，用于排版、布局、状态及视觉审阅；只在用户明确要求对应流程时进入其 `craft`、`shape` 等子命令。不因安装在某个 App 内，就把 App 的产品定位、配色、字体和待办列表布局当作赛事页面的设计需求。
- 没有该技能时，直接使用下述赛事专用准则，不要求安装新技能或引入框架。已有赛事模板或用户参考先检查可复用结构，不能只换标题与颜色。
- 用户要求直接生成或验证技能时，根据赛事与使用目的作出设计选择并继续；视觉摘要是说明，不额外增加审批。只有用户指定的设计流程明确要求确认时，遵循其确认要求。

## 生成前写一个具体的视觉摘要

先完成下面的本届视觉素材核实，再写摘要，不能先随机选配色再套赛事名称。

## 本届主图、slogan 与工具图标

- 每个新赛事页面都包含本届赛事的宣传主图、官方 slogan（如已发布）和专属工具图标。先打开当届官网、赛事指南或官方宣传稿，确认届次、素材与 slogan 的对应关系；不要拿游戏通用海报、往届主图或 AI 编造标语当本届官方素材。
- 优先使用可合法获取的官方主视觉，保存原始链接、发布页、版权归属、获取时间和包内路径。实际打开图片检查其内容，不只看文件名。宣传图中的标题、slogan、人物与标识要完整可读，使用保持比例的布局；手机端不能用大幅裁剪把这些关键信息切掉。
- 页面风格跟随该届主视觉：从图片提取主色、辅助色、明暗关系、字体气质、线条与构图语言，转成页面 token 和组件样式。信息密度与可访问性仍需独立处理。不得把某一种深色、电竞蓝或宿主 App 风格固定为所有赛事默认值；通用随机配色只能在没有本届视觉资料时作为明确标记的补充方案。
- 工具图标优先使用真实赛事 Logo：先查当届官方标识，未发布或无法取得时使用仍适用的赛事通用官方 Logo；不要用游戏 Logo、队徽、默认日历或自制字标替代已经可获取的赛事 Logo。记录来源页、素材链接、版权归属与获取时间，并实际打开图片核对。Logo 无法取得时说明缺口，再提供标明「自制，非官方 Logo」的后备图标；不使用图像生成重绘官方 Logo。
- Logo 单独保存为包内资源（如 `assets/competition-logo.png`），用于页面品牌区及适合的 favicon，并准备好导入图标。`add_tool` / `update_tool` 的 `icon` 接收 `data:image/<类型>;base64,<内容>`，不接收本地路径或图片网址；不能仅把 Logo 放入目录就认为工具箱会自动使用。图片解码后不超过 2 MB；使用 PNG、JPEG、WebP、GIF 或自包含 SVG，SVG 不引用外部字体、图片或脚本。保留比例和完整图形，优先选择适合小尺寸的官方符号版，不拉伸或裁掉标识。
- 根据 Logo 明暗显式选择 `icon_background`（`auto` 或六位十六进制颜色），防止透明 Logo 淹没在默认背景中。至少检查 32px 和 64px 下的辨识度，导入后回读 `icon` / `icon_background` 并打开 App 工具箱验收；准备文件与宿主实际使用要分别确认。手动导入时交付 Logo 文件，并说明在图标选择器中选取该本地图片。不要为图标生成运行时工具包或请求宿主权限。
- 找不到本届主图或 slogan 时，记录缺口并优先继续核实官方发布。确需生成补充宣传图时，以已核实的当届视觉作为参考，区分「官方素材」与「AI 补充视觉」，不得假称完整；不要静默省略主图，也不以渐变色块或占位框替代。
- 页面配置可增加 `branding`，保存 `edition`、`slogan`、`hero`、`icon`、`palette` 及相应来源/生成方式。官方素材保留版权与来源；自制素材记录生成方式或提示词。交付目录包含全部图片与图标，离线加载也能显示，不依赖图片热链。

## 视觉摘要

写清四项，可放在工作记录而不占页面：

1. **场景**：用户在何种屏幕、光线和使用频率下查看什么。例如白天桌面快速查明天的对阵，不能只写「电竞所以深色」。
2. **布局与密度**：哪块是主视图、怎样切日期、哪里看阶段与晋级；以实际宿主宽度衡量，主内容应尽早进入首屏。
3. **赛事辨识**：队伍/选手名称、真实标识、系列赛比分、局制和阶段如何组合。不能只写「专业、现代、好看」。
4. **视觉锚点**：用户给的参考、已读到的赛事站结构，或明确选定的信息版式；提炼信息组织，不臆造官方品牌或原样复制整站。

布局可随赛事选择，例如单日对阵板配日期轨、密集轮次表、瑞士战绩分组配主赛程、对阵树配比赛详情。不要为所有赛事规定同一皮肤。

## 赛事信息要形成视觉单位

- 一场比赛的时间、双方、比分/待赛、局制是一个整体。大屏不能把双方散落在整页两端，中间留大片无用途的空白；长名与短名都检查。
- 双方对阵的比赛行按「主队名—主队徽—比分/VS—客队徽—客队名」排列，两个队徽紧邻比分区并在其两侧镜像对称；主队名靠右、客队名靠左，名称置于各自队徽外侧。对阵区域使用两侧等宽、中央固定的列或等效布局，不让队名长度、时间栏或右侧操作按钮挤偏比分中心。队徽保持完整比例；长队名可换行或省略并提供完整名称，窄屏可将时间、场地与操作换行，仍保留中间队徽和比分的顺序与对齐。
- 调整比赛行布局时保留点击语义：队名与队徽进入对应队伍详情，比赛其余可点击区域进入单场详情；详情、待办、关注等独立按钮各自响应，不因容器点击或排列变化误触其他操作。
- 名称与标识有清晰层级。团队赛事必须按 [队伍资料](team-profiles.md) 实际查找每队真实队标、介绍与可查的本届名单；文字后备仅用于加载失败或已说明的缺口，不能把文字方标当作完整交付。不能伪造官方队徽，也不能让破图占位。
- 赛程首屏优先：短标题与当前阶段后尽快出现真实对阵。通常不要让欢迎文案、巨型下一场横幅和多行筛选占去半屏以上。日期与阶段是主要导航；更多条件可折叠，不机械地平铺全部原生表单。
- 连续比赛适合紧凑的比分行；信息独立时才使用卡片。局制、系列赛比分、比赛状态与时间分层，不能全是同级黑字，也不能用颜色代替状态文字。
- 次要信息有明确位置：阶段进度、晋级条件与最近结果可作为辅助栏；窄屏移到主赛程之后或折叠。来源与 AI 提示词保留独立入口，避免混入主要观赛路径。
- 「赛制与晋级」按 [阶段进程参考](progression-views.md) 实际生成比赛卡与连线，显示胜负和流转；逐阶段检查，不能只有赛制文字、比分列表或战队按钮。
- 控件共享一套尺寸、边框和选中态；触屏主操作应容易点按。关注、选中日期、待定席位、无结果与过期快照都有真实可用状态。
- 未开赛只写计划开赛；已经过了时间但没有结果，不继续冒充「下一场」。更新时间明确为资料快照，不做假直播、假刷新或虚构倒计时精度。

## 三项验收分别记录

| 验收 | 要观察的证据 | 不能据此声称 |
| --- | --- | --- |
| 数据 | 结构校验明确 `ok: true`，事实来源与时区、未知字段核对 | 页面好看、线上实时可用 |
| 交互 | 实点日期/阶段、参赛者详情、关注、来源与复制；检查空状态、过期及偏好保存 | 已通过视觉评审 |
| 视觉 | 打开实际渲染截图并审阅桌面、宿主宽度和手机布局 | 用户已认可，或其他赛事也通过 |

视觉审阅至少看主赛程、参赛者详情和来源视图，覆盖约 1280、860、390 像素宽度；宿主实际宽度不同时以它补测。检查主图与本届一致、slogan 可读、图标实际加载、整体风格与官方视觉的关联，以及第一屏对阵可见度、双方的距离与对齐、队名是否位于队徽外侧、两个队徽是否围绕比分对称、长短队名和右侧按钮是否导致中心偏移、留白是否服务信息、长名换行、文字对比、选中态与手机触控。横向日期轨可以在自身区域滚动，页面整体不能横向溢出。

先输出真实的自评问题，再按问题修正并重拍；没有发现问题可以如实说明，不强行凑修改次数。最终显示主视图截图，让用户可以判断视觉结果；不要只给「已优化」「测试通过」。

## 用案例验证技能修改

修改页面生成或视觉流程并验证完整生成效果时，从修改后的技能重新生成完整页面，不在旧 HTML 上只补样式后称为完整生成流程验证。用户要求原位调整既有赛事页的局部布局时，在完整副本中修改并按三项验收检查实际页面，明确这次只验证对应布局规则，不为验收额外创建赛事工具。仅调整 Logo 选取与导入说明时，验证素材来源、导入参数和工具箱实际显示即可。可复用已核实且仍适用的数据，保留其原成功时间与来源；没重新获取的事实不能刷新成功时间。新的页面和工具使用新身份，除非用户要求原位更新。

记录技能参考路径与文件摘要、使用的赛事和范围、生成包位置、三项验收、截图及剩余限制。案例文件留在临时目录或用户指定交付处，不把 LoL 队伍、配色、赛程或本次评分写成所有赛事的固定模板。单个 LoL 案例只证明这次流程和产物，不代表跨项目全面验证。
